# R12: Environment parity in Claude Code (cloud / local / Windows / phone): mechanisms, practices and community solutions (October 2026)

**Short answer:** You can't get full parity, and the official docs show why. A cloud session uses a different settings model than a local one: it reads the repo's `.claude/settings.json` only when the session has a single repository, it never reads `~/.claude` or device-managed policy, it pre-approves file edits, and it has no bypass mode.\[1\]\[2\]\[3\] The approach that works is to stop assuming "identical" and design for the differences:
- one portable layer committed to the repo (exec-form Node/Python hooks gated on `CLAUDE_CODE_REMOTE`);
- server-side guarantees that don't depend on the client (GitHub branch protection, server-managed settings);
- a measured environment matrix (a SessionStart self-check plus CI on Windows, macOS and Linux).

## TL;DR
- **The "identical in cloud and locally" claim is false by documentation.**
  - A cloud session reads the shared `.claude/settings.json` only when it has one repository. User and local settings are "not read", and device managed-settings "doesn't reach a cloud session".
  - Cloud sessions "pre-approve file edits regardless of mode", and bypass mode isn't available there.
  - With several repositories, "a session with several repositories doesn't load hooks from any repository's `.claude/settings.json`".
- **There are hard blocks, but only server-side.**
  - **Bypass:** `permissions.disableBypassPermissionsMode: "disable"` in managed settings blocks bypass locally. In the cloud you need server-managed settings, because the MDM file doesn't reach a cloud session.
  - **Pushes to main:** GitHub branch protection or rulesets. The cloud GitHub proxy "doesn't limit which branches a push can update". There are also documented bugs where a cloud push went to `main` anyway (#44949).
  - **Hooks that fail:** `onFailure: "block"` (v2.1.295+) closes hooks fail-closed.
- **For Windows and the other differences, portability is designed in, not assumed.**
  - Exec-form hooks (`command` + `args`, no shell, v2.1.139+) that call `node`/`python` scripts with no dependence on jq or Git Bash.
  - State kept in the project directory or git, not in `/tmp` or `%TEMP%`.
  - Every run checks the environment it is in: a SessionStart self-check, `/status`, `/hooks`, `claude doctor`, and a CI matrix.

## Key Findings

### 1. Which configuration loads where (verified, official docs)

| Element | Local CLI / Desktop / IDE (macOS, Linux, WSL, Windows) | Cloud, 1 repo (web, mobile app, `--cloud`, routines) | Cloud, several repos (Anthropic-hosted) | Remote Control (phone → local session) |
|---|---|---|---|---|
| `~/.claude/settings.json` (user) | Yes | **No** | **No** | Yes (the machine's local config) |
| `.claude/settings.json` (project: allow/ask/deny, hooks) | Yes | Yes | **No**: no repo's hooks load | Yes |
| `.claude/settings.local.json` | Yes | **No** | **No** | Yes |
| Device `managed-settings.json` / MDM | Yes | **No** | **No** | Yes |
| Server-managed settings (claude.ai console) | Yes (when signed in to the org) | Yes (except Claude Tag) | Yes | Yes |
| Repo `CLAUDE.md`, `.claude/rules/`, skills, agents, commands | Yes | Yes | CLAUDE.md loads (#89215) | Yes |
| `~/.claude/CLAUDE.md`, user skills/agents | Yes | No (workaround: a setup script writes `~/.claude/CLAUDE.md`) | No | Yes |
| Plugins from `enabledPlugins` in the repo | Yes | **No** | No | Yes |
| Bypass mode | Yes (unless blocked by managed settings) | **Unavailable** | Unavailable | Not selectable from the app |
| File edits | According to the mode | **Always pre-approved** ("Accept edits" = `default`) | Same | According to the mode |

What this means for R12: the claim that `ask` rules work "identically" is untrue in three places. In the cloud they load only with one repository. File edits are pre-approved there anyway. And in multi-repo sessions they disappear entirely, with no warning: issue #89215 describes "There is no error. That is the defect."\[4\]

### 2. Permission modes and hard blocks
- **Plan locally is not a hard block.** Per the docs, in interactive terminal sessions with bypass available, planning commands get neither the classifier nor a prompt, and approving a plan can switch the session to "BYPASS PERMISSIONS".\[2\] So plan mode only becomes a hard block once bypass is removed from the cycle.
- **`defaultMode: "bypassPermissions"` from the project file is ignored.** Set in `.claude/settings.json` or `.local.json`, it doesn't take effect and the session starts in Manual.\[2\] But the bypass flag passed from the CLI still works.\[5\]
- **Deny rules block in every mode, including bypass.** `ask` rules are also never auto-approved in any mode.\[2\] That makes them the most portable gate, but only where the settings file actually loads.
- **The hard local block** is `permissions.disableBypassPermissionsMode: "disable"` in managed settings.\[2\] It is a "lock": the strictest value from any source wins. Claude Code reads it only under `permissions.`, not at the root.\[6\]\[7\]
- **In the cloud, `dontAsk` and `bypassPermissions` from settings files are ignored.**\[5\] The available modes are Accept edits, Plan and Auto.\[2\]

### 3. Git branch: cloud vs local
- **Cloud:** each session works on its own branch.\[8\] Routines push only to `claude/*` by default, unless "Allow unrestricted branch pushes" is on.\[9\]\[10\]\[11\]
- **Documented bugs both ways:**
  - #44949: a scheduled task pushed to `main` even though the option was off.\[12\]
  - #58141: a push to `main` got a 403 even though the option was on.\[13\]
- **The cloud GitHub proxy blocks only branch deletions and pushes of anything other than a branch** (tags, for example). It "doesn't limit which branches a push can update" and recommends branch protection or rulesets.\[1\]
- **Locally there is no guard at all.** A Stop hook copied from the cloud would push from `main` (the `AKTUALIZUJ.bat` setup).

### 4. Environment detection
- **`CLAUDE_CODE_REMOTE`** is `"true"` in cloud sessions and unset in the local CLI. This is the official way to gate cloud-only setup.\[1\]\[14\]\[15\]
- **`CLAUDE_CODE_REMOTE_SESSION_ID`** is set in cloud sessions. **`CLAUDE_CODE_BRIDGE_SESSION_ID`** is set while a Remote Control connection is active (v2.1.199+).\[1\]\[14\] That lets you tell "the phone is driving a local session" apart from "a cloud session".
- **`CLAUDE_PROJECT_DIR` and `cwd`** come with caveats:
  - In multi-repo cloud sessions `CLAUDE_PROJECT_DIR` was empty (#89215; also #33815).\[4\]\[16\]
  - In worktrees `CLAUDE_PROJECT_DIR` stays at the starting root, and the hook's `cwd` field follows Claude.\[14\]
- **OS detection** has no Claude-specific variable. Use `process.platform` / `sys.platform` in the script. That is one more reason to write hooks in Node or Python.

### 5. Ephemeral vs persistent state
- **A cloud VM** pauses after a few minutes of inactivity with its files saved. It can then be reclaimed.\[1\] After that, only the conversation history is restored; running background work, subagents and the self-paced `/loop` wakeup are not.\[1\]\[17\]
- **The setup-script cache** is a filesystem snapshot (about 7 days, and only if the script finishes in about 5 minutes). It keeps files, not processes.\[1\]\[17\]\[18\]
- **Conclusion for gates:** flags in `/tmp` or `%TEMP%` are environment-dependent and can disappear.
  - Keep state in the project directory, e.g. `.claude/state/` in `.gitignore`.
  - If it must survive a VM reclaim and travel cloud↔local (teleport moves the branch), it has to be committed to git or reconstructable from git (for example, a marker derived from the commit or branch state).
  - `CLAUDE_ENV_FILE` (SessionStart, Setup, CwdChanged, FileChanged) carries variables only for the current session.\[14\] It is not storage.

### 6. Windows
- **Hook shell:** shell-form hooks run in `sh -c` on macOS/Linux, in Git Bash on Windows, and in **PowerShell when Git Bash isn't installed**.\[19\]\[20\] Since 2.1.120 Git Bash isn't required.\[14\]\[21\]\[22\] One hook can therefore run under three different shells.
- **Exec form** (`args`, v2.1.139+) uses no shell and substitutes `${CLAUDE_PROJECT_DIR}` itself. On Windows `command` must be a real `.exe` (e.g. `node`), not a `.cmd` shim.\[14\]\[23\]
- **Permission paths** are normalized to POSIX form before matching (`C:\Users\alice` → `/c/Users/alice`).\[24\]\[25\]\[26\] Per #65187, the v2.1.162 changelog notes a fix for backslash and case-variant rules that never matched.\[27\] Older reports: #40170 (case-sensitive matching), #46783 (the prompt generated backslash allow-rules).\[28\]\[29\]
- **Dependencies:** jq ships neither with Windows nor with Git for Windows (#14817, the jq error in the Ralph Wiggum plugin). `python3` is often the Microsoft Store stub, and the python.org installer doesn't create `python3.exe` (zilliztech/memsearch #774). Failures are silent.\[30\]\[31\]\[32\]
- **Backslashes in hook paths** are eaten as escape characters by Git Bash (#21878, #88578: "killed my memory hooks for 46 days").\[33\]\[34\]
- **CLAUDE_ENV_FILE in PowerShell:** PowerShell commands receive the variables from v2.1.296, but the file is never executed.\[14\]\[35\]
- **Sandbox:** the Bash sandbox doesn't work on native Windows, only on WSL2.\[36\]\[37\]
- **Separate configs:** WSL and native Windows installs keep separate `~/.claude` directories.\[38\]

### 7. Backgrounding (fork mode)
- Fork mode is on by default in interactive sessions (since v2.1.232) and off in `-p` and the Agent SDK. When it is on, **every** subagent runs in the background and Claude can't ask for the foreground.\[39\]\[40\]\[41\]\[42\]
- Overrides: `CLAUDE_CODE_FORK_SUBAGENT=0`, or `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1` (forces foreground everywhere, but kills background tasks).\[39\]\[41\]\[43\]
- Bugs:
  - #91225: on Windows (2.1.252), `run_in_background=false` is ignored under fork mode.\[44\]
  - #81439: a teammate's subagent is silently launched async.\[43\]
- In the cloud, background work doesn't survive a VM reclaim.
- Conclusion: a design that relies on a foreground subagent (e.g. a chain with gates) behaves differently in `-p`/CI than interactively.

### 8. Phone
- The Claude app is only a client. There are three different backends:\[45\]
  - **Cloud session:** cloud config (repo only).
  - **Remote Control:** the local session with the full local config.\[45\]
  - **Dispatch:** the Desktop app; Pro/Max only.\[45\]
- **The "phone prompt" isn't a separate configuration.** It is the prompt of whatever backend the session runs on. Bypass can't be selected from the app in either case. Commands such as `/plugin` and `/resume` don't work from the app.\[17\]\[45\]
- There is no official mechanism to test or inspect "what the phone prompt looks like". The workaround is to run `/context` and `/status` from the phone in each mode.

### B. How the biggest players do it
- **Anthropic (official):**
  - **Configuration in the repo.** The "Claude Code: Best practices for agentic coding" post (Apr 2025) recommends committing `CLAUDE.md` and `.claude/settings.json` ("we recommend checking the former into source control to share with your team").\[46\]
  - **Verification in CI.** The "How Anthropic teams use Claude Code" PDF (2025) recommends "Set up Claude to verify its own work by running builds, tests, and lints automatically" and describes using GitHub Actions.\[47\] It doesn't mention cross-OS parity or branch protection.
  - **Devcontainer for consistency.** The devcontainer docs: "Run Claude Code inside a dev container for consistent, isolated environments across your team". An earlier version said: "Mirror your devcontainer configuration in CI/CD pipelines".\[48\]\[49\]
  - **Hardened CI workflows.** In `claude-code-action`, Anthropic forces `--permission-mode auto` in every workflow and has a `workflow-hardening.yml` check that fails the build when protection is broken.\[50\]
  - **MDM templates.** `examples/mdm` in anthropics/claude-code has templates for Jamf, Intune and Group Policy (`Set-ClaudeCodePolicy.ps1` writes `C:\Program Files\ClaudeCode\managed-settings.json`).\[51\]
  - **GitLab CI** support is in beta.\[52\]\[53\]
- **Organizations (anecdotal):**
  - **Our World in Data** (docs.owid.io) states openly that cloud sessions get the repo's `CLAUDE.md`, skills, agents and the SessionStart hook "but not your personal ~/.claude/CLAUDE.md". They build the venv with `scripts/remote_setup.sh` wired as a SessionStart hook.\[54\]
  - **Omnissa Workspace ONE** has a guide to MDM rollout on Windows, macOS and Linux (`HKLM\SOFTWARE\Policies\ClaudeCode`).\[55\]
  - **Ascending** (blog): "A laptop policy does not automatically reach an Anthropic-hosted cloud session. Treat terminal, IDE, Windows, WSL, and hosted execution as separate rollout entries."\[56\]
- **Gap:** I found no large-company engineering blog on a cross-OS or cloud↔local parity matrix for Claude Code.

## Recommendations (prioritized)
1. **Turn on GitHub branch protection or rulesets on `main` now.** It is the only guard that works the same in the cloud, locally and from the phone, and it covers the documented proxy bugs (#44949).\[10\]\[67\]
2. **Remove the "identically in cloud and locally" claim** and replace it with the loading table from Section 1 of Key Findings in the project docs.
3. **Hard local block:** `permissions.disableBypassPermissionsMode: "disable"` (and possibly `disableAutoMode`) in managed settings. For the cloud, deliver critical deny and ask rules through server-managed settings.
4. **One portable Stop/commit hook in Node, exec form.** It:
   - refuses when the branch is `main`/`master`;
   - pushes only from feature branches;
   - is gated on `CLAUDE_CODE_REMOTE` or an explicit opt-in;
   - has a kill switch.

   Change `AKTUALIZUJ.bat` to finish on a working branch, and add a git `pre-push` hook as defense in depth.
5. **Rewrite every hook** to `"command": "node", "args": ["${CLAUDE_PROJECT_DIR}/.claude/hooks/x.mjs"]`. No jq, no `python3`. Add `onFailure: "block"` on gating PreToolUse hooks.
6. **Move gate state** from `/tmp` / `%TEMP%` to `.claude/state/` (in `.gitignore`), or derive it from git. Don't assume it survives a VM reclaim.
7. **SessionStart self-check** (Node), reporting:
   - OS;
   - `CLAUDE_CODE_REMOTE` and `CLAUDE_CODE_BRIDGE_SESSION_ID`;
   - whether `CLAUDE_PROJECT_DIR` is empty;
   - the branch;
   - whether `node`/`git`/`jq` are present;
   - permission mode.

   It returns `additionalContext` and a warning on `main` or in multi-repo.
8. **CI matrix:** hook tests on windows-latest (Git Bash, PowerShell 5.1 and 7), ubuntu and macos, plus one manual end-to-end test per environment: cloud with 1 repo, cloud multi-repo, local Windows, local Linux, phone via Remote Control.
9. **Pin fork mode** (`CLAUDE_CODE_FORK_SUBAGENT`) in the settings `env`, and don't design agent chains that rely on a foreground subagent.
10. **Multi-repo:** for gated work, use one repo per session. If that's unavoidable, use a setup script that merges hooks into `~/.claude/settings.json`.

## Caveats
- Claude Code changes fast. The versions cited (v2.1.139 exec form, v2.1.162 Windows path fix, v2.1.232 fork default, v2.1.295 `onFailure`, v2.1.296 CLAUDE_ENV_FILE in PowerShell) come from the docs as of October 2026. Check them with `claude --version`.
- GitHub issues are user reports. Their states (open/closed) and dates weren't fully verified. #89215 ties the missing settings to multi-repo as a hypothesis; the docs separately confirm that limitation.\[1\]\[4\]
- Third-party blogs (claudefa.st, morphllm, systemprompt.io) can be inaccurate. systemprompt.io gives wrong managed-settings paths.\[68\]
- I found no public big-company write-up on a cloud↔local↔Windows parity matrix. The "big players" section relies mostly on Anthropic's own materials.
- Community PRs are often marked "not tested in a real cloud session". Treat them as patterns, not proven solutions.\[69\]
