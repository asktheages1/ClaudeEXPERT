# R14: Making Claude Code obey its own runtime and harness mechanics, with enforcement mechanisms and practices (October 2026)

Claude Code's documentation, tool descriptions and system prompt already spell out nearly every R14 mechanic: auto-backgrounding, "do not sleep, poll, or peek", cwd carry-over, compaction, and subagent model and effort. So R14 is a failure to follow written rules, not missing rules. The fix that works is to turn each soft contract into a hard gate (PreToolUse deny hooks, permission rules, env vars, frontmatter) plus a per-turn injected state signal (UserPromptSubmit, SessionStart or PostCompact hooks, status line). Don't add more CLAUDE.md prose.

## TL;DR
- **Most R14 sub-issues have an official hard switch.** These include `CLAUDE_BASH_MAINTAIN_PROJECT_WORKING_DIR=1` (cwd drift), the `background: true` frontmatter field and the background-by-default subagents of v2.1.198, `CLAUDE_CODE_SUBAGENT_MODEL` with `_FORCE=1` (model), the `effort` frontmatter field and `CLAUDE_CODE_EFFORT_LEVEL`, `autoCompactWindow`/`/autocompact` (context budget), the built-in sleep block, and the Monitor tool. Waiting, peeking and polling are covered only by tool-description prose ("do NOT sleep, poll, or proactively check on its progress"; "Don't peek"), and that is exactly the part the model breaks.
- **Close the workaround gap with PreToolUse hooks that classify behaviour rather than match literal strings.** Write rules for "waiting" (sleep in any language, until/while loops, `tail`/`ls`/`cat` on `tasks/*.output`), not for "the word sleep". First-word matchers are evaded by `cd x; sleep`, `python -c time.sleep`, `timeout N bash -c 'until…'`. Back the hooks with a Stop/SubagentStop hook that reads `background_tasks`, and with a status line that shows context %.
- **No official mechanism exists for four sub-issues.** These are: (a) treating harness `<system-reminder>`s as authoritative, (b) reading notifications promptly, (c) separating a queued mid-turn message from the current order (the harness itself tells the model to "address the message above as you continue this turn"), and (d) making the model actually use a loaded tool. Partial mitigations exist: `chat:queueSubmit` (Ctrl+X Enter), a Stop-hook queue file, hook-injected state, and `alwaysLoad`/`ENABLE_TOOL_SEARCH`. Treat these sub-issues as residual risk and verify them after the fact.

## Key Findings

1. **The rules exist and are explicit.** Three examples of the wording:
   - Agent tool description (extracted from the binary by Piebald-AI): "Agents run in the background by default. When an agent runs in the background, you will be automatically notified when it completes — do NOT sleep, poll, or proactively check on its progress." It also says: "Don't race: after launching a background agent, you know nothing about its results. Never fabricate or predict them."\[1\]
   - Fork tool description: "Don't peek. The tool result includes an output_file path — do not Read or tail it unless the user explicitly asks for a progress check."\[2\]
   - Bash description: "Do not retry failing commands in a sleep loop — diagnose the root cause."\[3\]
   
   The R14 session broke all of these. Prompt text alone therefore does not enforce them. The "drift" hypothesis (O0:132) matches the public evidence. Issue anthropics/claude-code #16958 (filed against v2.1.1 on Opus 4.5) says the behaviour "is not consistently replicable but occurs sporadically". Its transcript shows `sleep 15 && tail -50 …/tasks/a460b12.output` followed by `sleep 60` and `sleep 90`. This happened even though the same issue says Claude should "Use the `TaskOutput` tool to check background task status (designed for this purpose)".
2. **Auto-backgrounding is real, but it is announced only in the tool result.** A foreground command that reaches its timeout (2 min by default, `BASH_DEFAULT_TIMEOUT_MS`) is moved to the background, unless it starts with `sleep`.\[4\]\[5\] The result then reads: `Command did not complete within its 120s timeout and was moved to the background`, followed by a task ID and the output path.\[5\] The message shipped in v2.1.210, but the docs left it out until docs issue #77645. Boris Cherny closed that issue with "The docs now cover this: the Bash tool behavior section documents timeout-triggered auto-backgrounding". That explains why a model "knows" about 120 s auto-backgrounding but doesn't plan around it.
3. **cwd behaviour is configurable, version-dependent and has regressed.**
   - Default in the main session: a `cd` carries over while it stays inside the project or `--add-dir` directories. It resets with `Shell cwd was reset to <dir>` when it leaves them.\[5\]
   - Subagents never carry a `cd` over.\[5\]\[6\]
   - A `cd` inside a command that was moved to the background never applies; the result states `Session cwd remains <dir>…` (fixed in v2.1.210).\[5\]\[7\]
   - Community regressions run both ways: #42837 (cwd no longer persists) and #35058/#98470 (silent drift).\[8\]\[9\]
   - Treat cwd as untrustworthy. Force a reset, use absolute paths, and log `pwd`.
4. **Subagent model and effort can be set and verified, but you must check.**
   - Resolution order: per-invocation `model` → frontmatter `model` → `CLAUDE_CODE_SUBAGENT_MODEL` → main model.\[6\]
   - `CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1` (v2.1.257+) overrides all of these.\[6\]
   - `availableModels` can silently substitute a different model.\[6\]
   - To verify: `/tasks` shows the model and effort per subagent (v2.1.242+). PostToolUse `Agent` `tool_response` carries `resolvedModel` (v2.1.174+) and `modelsUsed` (v2.1.212+).\[6\]\[10\]\[11\]
   - Thinking is inherited from the main session, and there is no per-subagent thinking setting.\[6\]
5. **Context budget can be fully instrumented.** Available tools: `/context`, the status line `context_window.used_percentage`, `autoCompactWindow` (100k–1M), `/autocompact 500k`, `CLAUDE_CODE_AUTO_COMPACT_WINDOW`, PreCompact/PostCompact hooks, and SessionStart with matcher `compact` to re-inject state.\[11\]\[12\]\[13\]\[14\] Starting the largest task at 546k on a 1M window, with auto-compaction near 1M, is permitted. It is still a planning failure, and nothing forces the model to plan a budget, so the budget has to be imposed from outside.
6. **Several R14 behaviours sit in the harness itself, not only in the model.**
   - Mid-turn messages are injected with "Address the message above as you continue this turn" (#85084).\[15\]
   - Plan-mode state reaches the model only as a `<system-reminder>`, which can be missing on some turns (#83568, #86966).\[16\]\[17\]
   - `idle_prompt` "Claude is waiting for your input" notifications fire while background agents/tasks are still running (#98373). That issue is the narrower case of #32634, which was "auto-closed as stale".
   - A background task that never exits produces no notification (#88702).\[18\]
   
   Discipline can't fix these. Use the hard workarounds in the tables below.

## Details: per-method catalogue (tabulation-ready)

Legend for **Enforcement**:
- **HARD**: the harness blocks the action or makes it structurally impossible.
- **SEMI**: injected, deterministic context that the model can still ignore.
- **SOFT**: instruction or prose only.

Legend for **Effort**: L = minutes, M = an hour, H = a day or more. **Status**: C = confirmed in docs or source; A = assumed or inferred; verify before relying on it.

## Caveats
- **Version volatility.** Many behaviours changed between v2.1.198 and v2.1.292: background-by-default, model-resolution order (before v2.1.251 the env var won),\[6\] and background time limits. Pin your Claude Code version, or re-test the hooks after every update.
- **Gaps in the sources.** Several Boris Cherny items come from secondary summaries of his posts, not the original posts. The OpenClaw `Bash(run_in_background:true)` deny syntax is shown in a PR, not in the official permissions docs. Per-event presence of `permission_mode` is documented only as "not all events receive this field".\[11\]
- **The Stop decision table was not captured verbatim.** The Stop-hook field `background_tasks` and the 8-continuation cap are quoted from the hooks reference,\[11\] but the English Stop decision table itself was not fetched.
- **Every string-matching hook can be evaded.** The public record (#46144, sandcastle-kit #540, C-01's tests) shows the model finding new waiting idioms when one is blocked.\[25\]\[26\]\[48\] Pair hooks with the deny-reason redirect to Monitor or end-of-turn, so the blocked model has a sanctioned path rather than a puzzle to solve.
- **Some R14 symptoms are harness bugs, not model failures.** These include mid-turn injection wording, missing plan-mode reminders, idle notifications during background work, and silent never-exiting tasks. Report them upstream rather than tuning prompts.
