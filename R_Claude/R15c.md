# R15 Owner Communication and Standing Conventions in Claude Code: Every Known Fix, Ranked

The only reliable fix for R15 is to stop treating style and conventions as prompt text and turn them into checks that run at the moment of output or action: a Stop hook that lints the last assistant message (typography, word count, banned terms, untranslated English, internal labels) and blocks with a rewrite reason, plus PreToolUse hooks on `git commit`/`gh pr create` that refuse the action until the changelog entry, version bump and backup report exist. CLAUDE.md, output styles and prompt wording only raise the base rate. Anthropic's own docs say CLAUDE.md is "context, not enforced configuration" and point to hooks for anything that must happen every time.\[1\]\[2\]

## TL;DR

- **Root cause confirmed by Anthropic.** CLAUDE.md and output styles are probabilistic: "Claude treats them as context, not enforced configuration. To block an action regardless of what Claude decides, use a PreToolUse hook instead." Of the three R15 mechanisms (rules compete with content, nothing measures output, nothing checks at the moment of action), prompt-side fixes touch only the first. Hooks are the only native layer that covers the second and third.
- **Best combined stack.** (1) Short, positively phrased rules in CLAUDE.md plus a custom output style with `keep-coding-instructions: true` and the `language` setting. (2) A UserPromptSubmit/SessionStart hook that re-injects a five-line style card. (3) A Stop hook that lints `last_assistant_message` and blocks once with a concrete rewrite reason. (4) PreToolUse guards on commit/PR for ZMIANY, the version bump and the backup report. (5) A PostToolUse/PostToolBatch "silence counter" that asks for a one-sentence update after N silent tool calls. (6) A forced skill-evaluation hook that requires a stated reason when a skill is skipped. (7) `/doctor prompt-audit` plus a spell/stale-reference check for CLAUDE.md.
- **What you cannot fully fix.** A chat reply cannot be blocked before the owner sees it. A Stop-hook rewrite appears below the faulty reply. Read-deny rules hide file contents but probably not folder names in `ls`/Glob output. Read-vs-Bash has no official resolution beyond the fact that a single-file `cat`/`head` counts as a read. Mark those residual risks rather than expecting zero violations.

## Key Findings

1. **The official doctrine matches R15's diagnosis exactly.** The memory docs say the more specific and concise the instructions, the more consistently Claude follows them. They recommend a target of "under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence."\[3\] They also state that settings and hooks are enforced, while CLAUDE.md is "not a hard enforcement layer."\[1\]
2. **Prompt engineering guidance is specific and helps (a), (c) and (d), but it is advisory.** Anthropic's guidance covers four things. Tell Claude what to do instead of what not to do. Explain why a rule exists (the ellipsis/text-to-speech example). Match prompt formatting to the desired output. Use 3–5 examples.\[4\] For Opus 5, "the effort parameter controls how much the model thinks rather than how much it says," so length must be prompted explicitly. In a long system prompt, the instruction should be paired with "a short reminder near the end."\[5\]
3. **There is a documented conflict on emphasis.** The 2025 engineering blog recommended "IMPORTANT"/"YOU MUST."\[3\]\[6\] The current prompting guide says newer models "may now overtrigger" and that "CRITICAL: You MUST…" should be dialed back to normal language.\[4\] Alex Dunlop's review "CLAUDE.md Best Practices: What the Evidence Supports (2026)" says of the "IMPORTANT and YOU MUST framing" that "No study has tested it" and advises "Treat emphasis framing as untested folklore." Treat capitalised emphasis as unproven. Positive phrasing plus a reason plus an example is the officially supported pattern.
4. **Stop hooks are the main measurement layer and are now well specified.** Stop/SubagentStop receive `last_assistant_message`, which avoids the documented transcript-flush race.\[7\]\[8\] `decision: "block"` with a `reason` forces another turn.\[9\]\[10\] Since v2.1.163 `hookSpecificOutput.additionalContext` can give non-error feedback.\[11\] Claude Code caps consecutive Stop-hook continuations at eight by default (`CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`), and `stop_hook_active` must be checked to avoid loops.\[10\]\[12\]\[13\]
5. **Ready-made artifacts exist for (a), (b) and (h).** These include Anthropic's official `hookify` plugin (60,376 installs, markdown rules on bash/file/stop/prompt events),\[14\] `house-style-lint`,\[15\] `astrosteveo/plain-english`,\[16\] `jimbarritt` software-english-lint and `thrash-d/slop-linter` (50 Vale rules plus a PostToolUse hook).\[17\] They also include Mintlify's published setup: its CLAUDE.md says "Style rules: enforced by Vale (.vale.ini)", a PostToolUse hook runs `vale "$(jq -r '.tool_input.file_path // empty')"`, and a PreToolUse hook blocks `--no-verify` with `exit 2`. None of them handles Polish or the exact R15 rule set out of the box. All are configurable regex/Vale engines, so the work is writing the rule file.
6. **Changelog and version conventions are best enforced at `git commit`/`gh pr create` with PreToolUse.** In ken-mro/FlagsRally PR #165, a "New PreToolUse hook .claude/hooks/guard_changelog.py blocks gh pr create when the branch does not change CHANGELOG.md," with the opt-out "--label no-changelog only when the user asks." Pair this with a deny on `--no-verify` so a git pre-commit hook cannot be skipped.\[18\]
7. **Skill rules ignored without a reason (f) is a known platform weakness.** Scott Spence measured a "forced evaluation" UserPromptSubmit hook at 84% skill activation against 20% for a simple reminder hook.\[19\] obra/superpowers forces skill checks by injecting `using-superpowers` at SessionStart with the "1% chance… you ABSOLUTELY MUST invoke the skill" rule.\[20\]\[21\] Superpowers also states that user instructions in CLAUDE.md outrank skills, which is the hook for requiring a stated reason when deviating.\[22\]
8. **Long silences (d) now have official prompting levers.** Claude Fable 5.1 "writes fewer user-facing updates between tool calls," and the guidance is to "ask for progress text explicitly."\[4\]\[23\] For Opus 5.5, the guide tells harness builders to count consecutive tool-calling steps that give the user nothing to read.\[24\] In Claude Code that counter can be built as a PostToolUse or PostToolBatch hook. That part is assumed, not documented.

### 4. Effectiveness ceiling and design rules for the hooks

- **Block once, then allow.** Always check `stop_hook_active`, or the default 8-continuation cap ends the turn anyway.\[12\]\[13\] Give a specific `reason` (rule, offending text, replacement), because the reason becomes Claude's next instruction.\[10\]\[64\]
- **Use `last_assistant_message`, not the transcript.** Several plugins (supermemory, correctionguy, skill-olympus) shipped bugs from reading the transcript at Stop time.\[65\]\[66\]\[67\]
- **Strip code blocks and quoted text before linting.** Commands and paths legitimately contain dashes and parentheses. Otherwise the linter generates false blocks and Claude learns to ignore it.
- **Keep hooks fast.** One reply linter measured about 2 s per turn even with nothing to check.\[51\]
- **Expect visible rewrites.** No documented hook lets you suppress or replace a displayed chat reply before the owner sees it. A `MessageDisplay` event exists, but this research did not verify whether it can safely rewrite text, so treat it as unverified.

## Recommendations: ranked layered stack for R15

1. **Turn every owner rule into a measurable spec (L effort, prerequisite).** Replace "concisely" with a word cap, "no dashes" with an allowed-punctuation list, and "explain jargon" with a glossary file. Write it in the style you want back (O2, O3, O4, C-C4). Keep CLAUDE.md under 200 lines and move release rules to a path-scoped rule.\[1\]\[3\]
2. **Stop-hook reply linter: the core fix for (a), (b), (c), (f) and (h). Highest impact, M effort.** Start from astrosteveo/plain-english or house-style-lint, or a 60-line script. Check: banned characters in prose, numbers in prose, more than one file path per sentence, `\bH\d\b` labels, glossary terms, words over the limit, and a missing `Skill:` line. Block once with a precise rewrite instruction. Optionally add a `type:"prompt"` judge for unexplained jargon.
3. **PreToolUse commit/PR guard plus git pre-commit plus `--no-verify` deny: the core fix for (e). Highest reliability, M effort.** Deny the commit until ZMIANY, the version bump and the backup report are staged. Add a Stop-hook finish-line check for sessions that end without committing.
4. **Recency injection (L effort).** Use a UserPromptSubmit hook (or SessionStart with matcher `startup|compact`) that injects a five-line "owner card": language, word cap, punctuation, glossary pointer, update cadence. Add a custom output style with `keep-coding-instructions: true` and set `language: "polish"`.
5. **Forced skill evaluation with a stated reason for (f) (L effort).** Use a forced-eval UserPromptSubmit hook plus the Stop-hook `Skill:` line check.
6. **Silence counter for (d) (M effort).** Combine the cadence instruction, a PostToolBatch counter that injects an update request after N silent tool calls, and a statusline heartbeat.
7. **Tool-choice clarity for (g) (L effort).** State that `cat` satisfies read-before-edit and which source wins on conflict. Add a PreToolUse redirect only if the rule keeps being broken.
8. **Hygiene for (i) (L effort).** Run `/doctor prompt-audit` monthly, a spellcheck and stale-path check in pre-commit, and use `/hookify` to convert repeated corrections into rules, pruning dead rules.

What to skip: piling on capitalised emphasis (O5), very long CLAUDE.md rule lists, and relying on skill auto-invocation or the `language` setting alone. Primary GitHub issues show all of these failing for style and language rules.\[31\]\[33\]\[62\]
