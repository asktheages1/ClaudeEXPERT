# R09 — Open Items Without Tracked State in Claude Code: Mechanisms, Tools and a Reference Architecture

Claude Code has no built-in "obligation ledger", and nothing in it guarantees that every owner remark gets a disposition. You can still close this gap reliably by combining four pieces: (1) a structured ledger file in the repo, edited only through a script; (2) a deterministic Stop/PreToolUse gate that refuses "done", session end or `gh pr create` while items are open or carry no reason; (3) a SessionStart(`startup|resume|compact`) hook that re-injects the open items; and (4) a fresh-context verifier subagent that reconciles the ledger against the owner's verbatim messages. Native Tasks, `/goal`, the TaskCompleted hook and Anthropic's own "feature list with `passes: false`" harness each supply part of this, but none covers dispositions with reasons, risks, owner decisions or knowledge-gap choices.

## TL;DR

- **Official building blocks exist, but none is a ledger.** Tasks (`TaskCreate/TaskUpdate/TaskList/TaskGet`) persist across compaction and, with `CLAUDE_CODE_TASK_LIST_ID`, across sessions. However, they only track pending/in_progress/completed, have no reason field, and are no longer on by default on the newest models. Stop, TaskCompleted and PreCompact hooks can block. SessionStart with the `compact` matcher is the only official way to put state back into context after compaction.
- **Anthropic's own practice is file-based state plus gating.** A JSON feature list where every item starts as `"passes": false` and agents may change only that field, a progress file (`claude-progress.txt` / `CHANGELOG.md`), git commits, and a "get your bearings" startup routine. Anthropic's docs explicitly recommend a Stop hook as the "deterministic gate" and a fresh subagent as the reviewer.
- **The recommended build is a custom "disposition ledger" plus hooks; adopt an existing tracker only if you want issue semantics.** Beads, Backlog.md, Task Master and CCPM persist tasks well, but none enforces "every remark gets open/done/partial-with-reason/rejected-with-reason/deferred-with-owner-decision". Stop-hook projects (todo-guard, session-end-issue hooks, Ralph) supply the blocking pattern. Compose them: ledger schema + write-through script + gates + re-injection + verifier.

## 1. Official recommendations and mechanisms (Anthropic)

### 1.1 Tasks (successor of TodoWrite) — verified

- **What it is.** Anthropic's announcement, published as an X article by Anthropic's Thariq (@trq212) on Jan 22, 2026 and reposted by Boris Cherny ("We've upgraded Todos => Tasks to help Claude complete longer projects"): "Today, we're upgrading Todos in Claude Code to Tasks… Tasks are stored in the file system so that multiple subagents or sessions can collaborate on them… Tasks are stored in ~/.claude/tasks, you can use this to build additional utilities on top of tasks as well." The feature was introduced in v2.1.16 (January 22, 2026), according to claudelog; per FlorianBruniaux's claude-code-ultimate-guide, Tasks became the default in v2.1.19 (2026-01-25), the release that added `CLAUDE_CODE_ENABLE_TASKS`.
- **Persistence.** The official interactive-mode docs say: "Tasks persist across context compactions, helping Claude stay organized on larger projects". To share a list across sessions: "set CLAUDE_CODE_TASK_LIST_ID to use a named directory in ~/.claude/tasks/: CLAUDE_CODE_TASK_LIST_ID=my-project claude".\[1\] The env-vars page: "Share a task list across sessions. Set the same ID in multiple Claude Code instances to coordinate on a shared task list".\[2\] `Ctrl+T` toggles the checklist.\[1\]\[3\] Without the env var, community guides report the list is session-scoped ("each claude invocation gets a fresh task list. Close session = tasks gone").\[4\]
- **Schema.** Per the Agent SDK `TaskListOutput`, a task has `id, subject, status: "pending"|"in_progress"|"completed", owner?, blockedBy[]`.\[5\] There is **no "partial", "rejected", "deferred", reason or owner-decision field**.
- **Model gating (important).** Per the tools reference, the task tools are on by default only for "Claude 3.x models, Opus 4 through 4.7, Sonnet 4 through 4.6, and Haiku 4.5".\[6\]\[7\] The official changelog (Week 33, Aug 10–14, 2026) states: "Todo/task-tracking tools (TaskCreate/Get/Update/List, TodoWrite) are no longer available on Opus 4.8, Sonnet 5, Fable 5, Mythos 5, and newer models; set CLAUDE_CODE_ENABLE_TODO_TOOLS=1 to bring them back". `CLAUDE_CODE_ENABLE_TASKS=0` switches to the legacy `TodoWrite`.\[2\]\[7\]\[8\]
- **Limitations for R09.** There are no disposition semantics, and the tool is repo-unaware: paddo.dev notes that reusing one list ID across repos means "Claude could pick up tasks from repo A while working in repo B".\[4\] The list lives in `~/.claude`, not in git, so the owner cannot review it in a PR.
- **Covers:** F9 and F10 partially (with a list ID); F5 partially. Does not cover F3, F4, F6 or F8.

### 1.2 Hooks — verified against the hooks reference (code.claude.com/docs/en/hooks)

| Hook | Role for R09 | Blocking? | Verified details |
|---|---|---|---|
| **Stop** | Closure gate before the turn ends | Yes — exit 2 or `{"decision":"block","reason":…}` | Input includes `stop_hook_active`, `last_assistant_message`, `transcript_path`. Claude Code "applies an 8-consecutive-continuation cap" (`CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`, default 8, `0` disables). A softer path, `hookSpecificOutput.additionalContext`, continues the turn without the hook-error label.\[2\]\[9\] |
| **SubagentStop** | Force auditor/verifier subagents to record findings before returning | Yes | Receives `agent_id`, `agent_type`, `agent_transcript_path`, `last_assistant_message`.\[9\] |
| **TaskCreated** | Require description / disposition fields when a Task is created | Yes — exit 2 or `decision:"block"` cancels creation\[10\] | "Use this to enforce naming conventions, require task descriptions…"\[10\] |
| **TaskCompleted** | Refuse completion without evidence | Yes — exit 2: "the task is not marked as completed and the stderr message is fed back to the model" | "Use this to enforce completion criteria like passing tests or lint checks before a task can close."\[9\] |
| **PreCompact** | Snapshot ledger and transcript; optionally block compaction\[11\] | Yes (added Week 16, Apr 2026): "Exit with code 2 to block compaction"\[9\]\[12\] | Cannot inject context: `systemMessage`/`continue` are discarded,\[9\] and PreCompact is not on the `additionalContext` list (inferred).\[13\]\[14\] |
| **PostCompact** | Logging only | — | Not a re-injection path.\[15\] |
| **SessionStart** | Re-inject open items | No (context only) | Matchers `startup`, `resume`, `clear`, `compact`, `fork`. `hookSpecificOutput.additionalContext` is added to context.\[9\]\[16\] |
| **UserPromptSubmit** | Capture every owner message verbatim; inject "N open items" reminder | Yes (can block prompt) | Stdout / `additionalContext` added to context. Default timeout lowered to 30 s.\[9\] |
| **PreToolUse** | Deny direct edits of the ledger; deny `gh pr create` / `git push` while items are open | Yes (`permissionDecision:"deny"`) | Docs warn the `if` filter is "best-effort, use the permission system… to enforce a hard allow or deny".\[9\] |
| **PostToolUse** | Validate ledger schema after every write | Feedback only (tool already ran) | `decision:"block"` + reason is fed back to Claude.\[9\]\[15\] |
| **SessionEnd** | Write handoff file | No | Short budget: hooks share 1.5 s unless the timeout is raised (max 60 s).\[9\] |

Other verified hook properties:
- **Handler types:** `command`, `http`, `mcp_tool`, `prompt` and `agent` (experimental).\[9\]
- **Prompt/agent Stop hooks:** they return `{"ok": false, "reason": "…"}` to continue the turn. The `reason` "is fed back to Claude as its next instruction".\[9\]\[17\]
- **Exit codes:** for most events "only exit code 2 blocks", and exit 1 is a non-blocking error.\[9\]\[18\]
- **Hooks are deterministic, CLAUDE.md is advisory.** The best-practices doc: "Unlike CLAUDE.md instructions which are advisory, hooks are deterministic and guarantee the action happens."\[19\]

### 1.3 `/goal` — verified (v2.1.139+, May 2026)

- `/goal <condition>` keeps Claude taking turns until a separate small model (Haiku by default) judges from the transcript that the condition holds. Conditions can be up to 4,000 characters.\[20\]\[21\]
- The official docs describe it as "a wrapper around a session-scoped prompt-based Stop hook".\[9\]\[22\] The best-practices guide lists it as the "across a session" gate.\[19\]
- **Limit:** the evaluator only sees what is in the transcript, so "all ledger items have a disposition" must be made visible, e.g., by printing `ledger check` output.\[21\]
- **Covers:** F11 within one session. Not F10 (the goal is restored on `--resume`, but turn counters reset).\[23\]

### 1.4 CLAUDE.md, memory and compaction — verified

- **What survives compaction.** "Project-root CLAUDE.md survives compaction: after /compact, Claude re-reads it from disk and re-injects it into the session."\[24\]\[25\]\[26\] Nested CLAUDE.md files and path-scoped rules are lost until a matching file is read again.\[27\]\[28\] Auto memory (`MEMORY.md`, first 200 lines / 25 KB loaded) is machine-local and also reloads.\[24\]\[26\]\[28\]\[29\]
- **Compaction instructions.** The best-practices doc: "Customize compaction behavior in CLAUDE.md with instructions like 'When compacting, always preserve the full list of modified files and any test commands'".\[19\] `/compact <instructions>` gives manual control.\[19\]\[30\]
- **Limitation:** CLAUDE.md is advisory. A "mandatory CLAUDE.md task" (F2) fails exactly because it depends on the model's attention. The docs themselves say: "If your CLAUDE.md is too long, Claude ignores half of it".\[19\] Use CLAUDE.md to *describe* the protocol and hooks to *enforce* it.

### 1.5 Verification and review guidance — verified (best practices)

- "Claude stops when the work looks done." Anthropic lists four escalating gates:\[19\]
  - **One prompt:** ask Claude to run the check and iterate in the same message.\[19\]
  - **`/goal`:** set the check as a session-wide condition.\[19\]
  - **Stop hook:** "a deterministic gate", one that "runs your check as a script and blocks the turn from ending until it passes".\[19\]
  - **Verification subagent:** a fresh model tries to refute the result, "so the agent doing the work isn't the one grading it".\[19\]
- **Adversarial review step:** "Before treating a task as done, have a subagent review the diff in a fresh context and report gaps." The docs also warn: "A reviewer prompted to find gaps will usually report some, even when the work is sound… Tell the reviewer to flag only gaps that affect correctness or the stated requirements".\[19\]
- **Evidence:** "Have Claude show evidence rather than asserting success."\[19\]
- **Owner interview:** "Interview me in detail using the AskUserQuestion tool… then write a complete spec to SPEC.md".\[19\] This is the closest official primitive for F8 (presenting choices to the owner), though it is not tied to any ledger.

### 1.6 Long-running harness guidance — verified (Anthropic Engineering, Nov 26 2025, "Effective harnesses for long-running agents")

- **Problem statement:** "each new session begins with no memory of what came before". "Compaction isn't sufficient… doesn't always pass perfectly clear instructions to the next agent." A later agent would "see that progress had been made, and declare the job done."\[31\]
- **Initializer agent:** creates `init.sh`, `claude-progress.txt` and an initial git commit, plus a comprehensive feature list. In the claude.ai clone example this was over 200 features, "all initially marked as 'failing'".\[31\]
- **Feature list format:** a JSON item with `"passes": false`. "We prompt coding agents to edit this file only by changing the status of a passes field… 'It is unacceptable to remove or edit tests'". Also: "the model is less likely to inappropriately change or overwrite JSON files compared to Markdown files."\[31\]
- **Coding agent:** each session starts by reading the progress file, git log and feature list, then picks "the highest-priority feature that's not yet done". It ends with a commit and a progress update, and marks items passing only "after careful testing".\[31\]
- **Code:** the `anthropics/claude-quickstarts/autonomous-coding` quickstart.\[31\]
- **Covers:** F5, F9, F10, F11. Gap: binary pass/fail only, with no reasons, rejections or owner decisions.

### 1.7 Agent SDK and API memory tool — verified

- **Memory tool.** `{"type": "memory_20250818", "name": "memory"}` is client-side: "Claude requests file operations, and your application executes them". Files "persist between sessions". The API adds a system prompt that includes: "ASSUME INTERRUPTION: Your context window might be reset at any moment, so you risk losing any progress that is not recorded in your memory directory." It is available on Claude 4+ and no longer needs a beta header.\[32\]\[33\]
- **Agent SDK:** it is relevant if you build your own harness; Tasks also work with `claude -p` and the Agent SDK.\[34\]

### 1.8 Where no official mechanism exists (explicitly)

- **No disposition taxonomy** (partial-with-reason, rejected-with-reason, deferred-with-owner-decision): no official mechanism.
- **No remark ledger** (owner message → item IDs → statuses): no official mechanism.
- **No risk register with mandatory decision:** no official mechanism.
- **No auditor-error log:** no official mechanism. SubagentStop can force one, but you must build it.
- **No "offer knowledge gaps to the owner as a choice" gate:** `AskUserQuestion` exists, but nothing forces its use.
- **No "PR contents checked against promises" check:** a custom PreToolUse gate on `gh pr create` or a reviewer subagent is required.

## 2. How the biggest players handle it in practice

- **Anthropic — long-running harness.** Uses the initializer + coding agent pattern, a JSON feature list with `passes`, `claude-progress.txt`, git and `init.sh` (see 1.6). Anthropic's own failure table maps "declares victory too early" to a feature-list file and "marks features as done prematurely" to "Self-verify all features. Only mark features as 'passing' after careful testing."\[31\]
- **Anthropic — scientific computing ("Long-running Claude for scientific computing").** The progress file `CHANGELOG.md` is "the agent's portable long-term memory… In CLAUDE.md, Claude was instructed to keep track of progress in this file". A good one tracks "current status, completed tasks, failed approaches and why they didn't work… and known limitations". It is paired with a test oracle and git.\[35\] Addy Osmani's summary describes the accompanying Ralph loop as one that "kicks the agent back into context whenever it claims completion and asks if it's really done".\[36\]
- **Anthropic — C compiler with 16 parallel agents.** Nicholas Carlini of Anthropic's Safeguards team ("Building a C compiler with a team of parallel Claudes", Feb 2026) reports: "Over nearly 2,000 Claude Code sessions and $20,000 in API costs, the agent team produced a 100,000-line compiler that can build Linux 6.9 on x86, ARM, and RISC-V." The harness relied on instructions to "maintain extensive READMEs and progress files that should be updated frequently with the current status", a Ralph-style loop, and tests as the oracle.
- **Anthropic product teams ("How Anthropic teams use Claude Code").** Recurring lessons are detailed CLAUDE.md files, checkpoint-heavy workflows, and a self-improving loop where Claude refines CLAUDE.md after sessions.\[37\]\[38\] The report contains nothing on obligation ledgers. This is an inference from the absence of such content, not a stated policy.
- **Anthropic — official plugin `ralph-wiggum` (anthropics/claude-code/plugins).** "This plugin implements Ralph using a Stop hook that intercepts Claude's exit attempts". The command is `/ralph-loop "<prompt>" --max-iterations <n> --completion-promise "<text>"`. Note: "The --completion-promise uses exact string matching… Always rely on --max-iterations as your primary safety mechanism."\[39\]
- **Other teams.**
  - **Automaze (CCPM)** uses GitHub Issues as "single source of truth… Issue state is project state".\[40\]
  - **Steve Yegge (Beads)** argues for replacing "that disgusting pile of half-eaten markdown files in your plans/ directory" with a dependency graph.\[41\]
  - **NVIDIA's Omniverse RTX Remix docs** describe a shared `.agents/` instruction set with Stop hooks and a compaction safety net at 50% context.\[42\]
  - Public, detailed descriptions of *disposition* ledgers from big companies were **not found**. Treat any claim of that kind as unverified.

- **obra/superpowers — `verification-before-completion`.** The Iron Law: "NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE". The superpowers plugin is listed at 245.3k on claudepluginhub (the metric is not specified).\[69\]\[70\]\[71\] Limitation: advisory (skill text), so pair it with a hook.

- **Prompt/agent Stop hooks:** an "Evaluate if Claude completed all requested tasks" prompt hook, documented in luongnv89/claude-howto and the official docs.\[72\]

## 5. Recommended combined architecture

The design is assumed: it is composed from the verified primitives above, not a published product.

### 5.1 Ledger (single source of truth, in git)

`.claude/ledger/items.jsonl` holds one JSON object per item, append-only history, and is edited only via `scripts/ledger` (CLI). The schema:

- `id` (e.g., `R-042`)
- `type` ∈ {commitment, owner_remark, mandatory_instruction, deferred_task, test, risk, open_question, knowledge_gap, auditor_error}
- `source`: the verbatim owner quote plus a message index, or the CLAUDE.md line
- `status` ∈ {open, done, partial, rejected, deferred}
- `reason`: required for partial, rejected and deferred; for partial it must name the dropped part
- `evidence`: command output, file path, commit SHA or PR section; required for done
- `owner_decision`: required for deferred, risk and knowledge_gap before closure; values are e.g. accept / defer-to-date / reject, plus the owner's quote
- `created`, `updated`, `session_id`

Why this shape:
- **JSON over Markdown** follows Anthropic's finding that the model "is less likely to inappropriately change or overwrite JSON files".\[31\]
- **Script-only mutation** mirrors Backlog.md's "mutations through CLI/MCP" and Anthropic's "edit only the passes field".
- **The owner-decision field** is what turns F6 and F8 into closable items.

### 5.2 Hook wiring

| Event | Script behaviour |
|---|---|
| **UserPromptSubmit** | Append the raw owner prompt to `.claude/ledger/owner-log.jsonl`. This makes F2 ("save first commission verbatim") deterministic instead of model-dependent. Then inject `additionalContext`: "Owner message #N logged. Register every remark in it with `ledger add` before acting; open items: K." |
| **PreToolUse** (`Edit|Write` on `.claude/ledger/*`) | Deny direct edits and point to `scripts/ledger`. Back this with a permissions `deny` rule, since `if` filters are best-effort. |
| **PreToolUse** (`Bash(gh pr create *)`, `Bash(git push *)`) | Run `ledger check --strict`. Deny if any item is open, if any partial/rejected/deferred item lacks a reason, if any risk/gap lacks an owner decision, or if any "done" lacks evidence. This covers "PR at the end after the audit" and unchecked PR contents (F1, F11). |
| **PostToolUse** (Bash calls to `scripts/ledger`) | Validate the schema and return `decision:"block"` with a reason on violation. |
| **TaskCreated / TaskCompleted** (if native Tasks are used) | Mirror tasks into the ledger. TaskCompleted exits 2 unless the mirrored item has evidence. |
| **Stop** | (a) If `stop_hook_active` is true or the block counter is ≥ 2 → allow. (b) If the last message is a question to the owner or a blocker report → allow. (c) If `ledger check` fails → block, listing up to ~10 item IDs. (d) Regex-scan `last_assistant_message` for deferral promises ("later", "in the summary", "will show", "next step I'll", "nadrabiam" (Polish: "I'm catching up"), "pokaże" (Polish: "will show"), "TODO") with no matching new ledger ID → block once: "Register this promise as a ledger item or fulfil it now." (e) Every owner-log entry must map to ≥ 1 ledger ID → otherwise block (F3). |
| **SubagentStop** (auditor/verifier types) | Block unless the subagent wrote its findings, including its own errors and false positives, as `auditor_error` items (F7). |
| **PreCompact** | Snapshot the ledger and transcript to `.claude/ledger/snapshots/`. Optionally block *auto* compaction once if the ledger has unsynced items (use sparingly). |
| **SessionStart** (`startup|resume|compact|clear`) | Inject `hookSpecificOutput.additionalContext`: open items grouped by type, items awaiting owner decision, the last 3 progress entries, and "run `ledger check` before claiming done". Stay under 10,000 characters and link the full file otherwise. |
| **SessionEnd** | Write `HANDOFF.md` from the ledger. This cannot block, and the time budget is short. |

### 5.3 Agents, commands and rules

- **`ledger-auditor` subagent** (read-only tools, fresh context). It reconciles owner-log ↔ ledger ↔ diff/PR body. It reports remarks with no item, "done" without evidence, partials without a reason for the dropped part, and promises in transcripts. It is told to "flag only gaps that affect correctness or the stated requirements", per the official over-reporting warning.\[19\] Invoke it from a `/close-out` command or an agent-type Stop hook.
- **`/close-out` slash command or skill.** It runs `ledger check`, then for every risk, knowledge gap and deferred item calls **AskUserQuestion** with explicit options (accept / defer with date / reject / research now) and records the answer verbatim in `owner_decision` (F6, F8). Finally it emits a disposition table into the PR body, with each item's ID, status, reason and evidence (F1, F4).
- **CLAUDE.md** (short): it states the protocol (every remark → ID; no "will do later" without an ID; done requires evidence; partial states the dropped part) and the compaction rule: "When compacting, always preserve all ledger IDs touched this session and any promises made to the owner."
- **Optional `/goal`** for long unattended runs: "`scripts/ledger check --strict` exits 0 and its output is shown".
- **Optional tracker backend:** swap the JSONL for Beads, Backlog.md or Task Master if you want boards, dependencies or GitHub visibility. Keep the gate scripts reading their JSON output (`bd ready --json`, Task Master `tasks.json`).

### 5.4 Rollout order (effort-ranked)

1. **Hours.** Ledger script + Stop gate + SessionStart injection + UserPromptSubmit verbatim log. This alone covers F2, F9, F10 and most of F11.
2. **About a day.** PreToolUse PR/push gate + PostToolUse schema validation + CLAUDE.md protocol (F1, F4).
3. **About a day.** Auditor subagent + `/close-out` with AskUserQuestion (F3, F6, F7, F8).
4. **Later.** Distribute to N projects as a **plugin** (hooks in `hooks/hooks.json`) or via managed settings,\[9\] which avoids per-project drift.\[9\] The "distribution of hooks to N projects" risk itself should be a ledger `risk` item with an owner decision.

## 6. Known pitfalls and limitations

- **Infinite loops.** Always check `stop_hook_active` and keep your own per-session counter. Claude Code overrides after 8 consecutive blocks (`CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`), but don't rely on that.\[75\]
- **Exit-code traps.**
  - Exit 1 does **not** block.\[9\]\[18\]
  - JSON is only parsed on exit 0; "JSON printed with exit code 2 is ignored".\[76\]
  - `additionalContext` must sit inside `hookSpecificOutput` with `hookEventName`. A top-level key is silently ignored (plur issue #1189).\[77\]
- **Stop fires on every response end,** not just at task completion,\[78\] and never on user interrupt.\[79\] The gate must allow questions to the owner and blocker reports, or it will force Claude to "continue" when it legitimately needs input.
- **PreCompact cannot speak.** Its output is not injected.\[9\] Use SessionStart(`compact`) to re-inject, or the marker + UserPromptSubmit trick.\[13\]\[14\]\[15\]
- **Gaming the checklist.** The model can mark items done, delete them, emit a Ralph `<promise>`, or edit the marker file. Mitigations:
  - append-only ledger with script-only writes and a PreToolUse/permissions deny;
  - mandatory evidence;
  - a git-diff check that item count never decreases;
  - an independent verifier subagent ("the agent doing the work isn't the one grading it").\[19\]
- **Reviewer over-reporting** leads to over-engineering.\[19\] Constrain the auditor's scope, as above.
- **Context bloat.** Injecting the full ledger every prompt wastes context. Inject counts plus open IDs, and keep the full file on disk.
- **Native Tasks caveats.**
  - Off by default on newest models (enable with `CLAUDE_CODE_ENABLE_TODO_TOOLS=1`).\[2\]\[80\]\[81\]
  - Repo-unaware list IDs.\[4\]
  - Not in git.
  - No reason fields.
- **Hook distribution to N projects.** User-level hooks apply everywhere but aren't shared; project hooks must be copied. Plugins and managed settings are the scalable routes. Cloud sessions don't read `~/.claude/settings.json`.\[9\]
- **SessionEnd** has a 1.5 s default budget,\[9\] so a heavy handoff generator (e.g., a Haiku call) may be cut off.\[2\] Do heavy work at PreCompact or Stop.
- **Advisory layers fail silently.** CLAUDE.md rules and skills (superpowers) improve behaviour but are not guarantees.\[19\] Every "must" in R09 needs a hook or permission rule behind it.
