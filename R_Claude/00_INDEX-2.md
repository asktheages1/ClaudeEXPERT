# [R09 — Open Items Without Tracked State in Claude Code: Mechanisms, Tools and a Reference Architecture](R09c.md)

## TL;DR

- **Official building blocks exist, but none is a ledger.** Tasks (`TaskCreate/TaskUpdate/TaskList/TaskGet`) persist across compaction and, with `CLAUDE_CODE_TASK_LIST_ID`, across sessions. However, they only track pending/in_progress/completed, have no reason field, and are no longer on by default on the newest models. Stop, TaskCompleted and PreCompact hooks can block. SessionStart with the `compact` matcher is the only official way to put state back into context after compaction.
- **Anthropic's own practice is file-based state plus gating.** A JSON feature list where every item starts as `"passes": false` and agents may change only that field, a progress file (`claude-progress.txt` / `CHANGELOG.md`), git commits, and a "get your bearings" startup routine. Anthropic's docs explicitly recommend a Stop hook as the "deterministic gate" and a fresh subagent as the reviewer.
- **The recommended build is a custom "disposition ledger" plus hooks; adopt an existing tracker only if you want issue semantics.** Beads, Backlog.md, Task Master and CCPM persist tasks well, but none enforces "every remark gets open/done/partial-with-reason/rejected-with-reason/deferred-with-owner-decision". Stop-hook projects (todo-guard, session-end-issue hooks, Ralph) supply the blocking pattern. Compose them: ledger schema + write-through script + gates + re-injection + verifier.

## 2. How the biggest players handle it in practice

- **Anthropic — long-running harness.** Uses the initializer + coding agent pattern, a JSON feature list with `passes`, `claude-progress.txt`, git and `init.sh` (see 1.6). Anthropic's own failure table maps "declares victory too early" to a feature-list file and "marks features as done prematurely" to "Self-verify all features. Only mark features as 'passing' after careful testing."\[31\]
- **Anthropic — scientific computing ("Long-running Claude for scientific computing").** The progress file `CHANGELOG.md` is "the agent's portable long-term memory… In CLAUDE.md, Claude was instructed to keep track of progress in this file". A good one tracks "current status, completed tasks, failed approaches and why they didn't work… and known limitations". It is paired with a test oracle and git.\[35\] Addy Osmani's summary describes the accompanying Ralph loop as one that "kicks the agent back into context whenever it claims completion and asks if it's really done".\[36\]
- **Anthropic — C compiler with 16 parallel agents.** Nicholas Carlini of Anthropic's Safeguards team ("Building a C compiler with a team of parallel Claudes", Feb 2026) reports: "Over nearly 2,000 Claude Code sessions and $20,000 in API costs, the agent team produced a 100,000-line compiler that can build Linux 6.9 on x86, ARM, and RISC-V." The harness relied on instructions to "maintain extensive READMEs and progress files that should be updated frequently with the current status", a Ralph-style loop, and tests as the oracle.
- **Anthropic product teams ("How Anthropic teams use Claude Code").** Recurring lessons are detailed CLAUDE.md files, checkpoint-heavy workflows, and a self-improving loop where Claude refines CLAUDE.md after sessions.\[37\]\[38\] The report contains nothing on obligation ledgers. This is an inference from the absence of such content, not a stated policy.
- **Anthropic — official plugin `ralph-wiggum` (anthropics/claude-code/plugins).** "This plugin implements Ralph using a Stop hook that intercepts Claude's exit attempts".   - **Automaze (CCPM)** uses GitHub Issues as "single source of truth… Issue state is project state".\[40\]
  - **Steve Yegge (Beads)** argues for replacing "that disgusting pile of half-eaten markdown files in your plans/ directory" with a dependency graph.\[41\]
  - **NVIDIA's Omniverse RTX Remix docs** describe a shared `.agents/` instruction set with Stop hooks and a compaction safety net at 50% context.\[42\]

# [Making Claude Code's Judgments Explicit, Exhaustive and Honest About Disagreement (R10)](R10c.md)

## TL;DR

- **Separate author from judge, and give the judge written criteria.** Anthropic's harness-design post found that agents "reliably skew positive when grading their own work" and that "tuning a standalone evaluator to be skeptical turns out to be far more tractable than making a generator critical of its own work".\[1\] Claude Code's best-practices docs recommend a fresh-context "adversarial review step".\[2\] Research shows self-preference survives even objective rubrics: Pombal, Rei & Martins (arXiv 2604.06996, a preprint, not confirmed peer-reviewed) tested on IFEval and LiveCodeBench and found that on HealthBench "SPB skews model scores by up to 10 points". So a cross-model judge or a judge ensemble is better than a same-model judge.
- **Exhaustiveness, scale consistency, dedup and label honesty are only reliable as code.** Use command hooks with exit code 2 or `decision: "block"` that validate a structured ledger: every evidence ID is covered, every severity comes from a frozen scale file, there are no duplicate keys, "accepted" requires a matching change, every "untested/unknown" claim carries an epistemic marker, and no trait words appear in causal analysis. Anthropic ships no validators for any of this. Prompts and CLAUDE.md are advisory only; the docs say so explicitly.\[2\]
- **Escalate, don't resolve silently.** Require a mandatory "Disagreements & Uncertainties for the owner" block, enforced by a Stop hook, and route it through AskUserQuestion in the main thread. Subagents, including reviewers, cannot call AskUserQuestion, so they must return questions to the main session instead of guessing.\[3\] The best ready-made community patterns are cross-model review tools that tag findings `[disputed]` (SameerKhan/model-crosscheck) and obra/superpowers' `receiving-code-review` skill ("IF any item is unclear: STOP … ASK for clarification").\[4\]\[5\]

R10's core failure is the author judging alone, with no labels and no route to escalate, which is exactly the configuration these vendors design out.

# [R11 — Making Claude Code design remedies with real option, impact and bypass analysis (v1)](R11c.md)

## TL;DR
- **No official "remedy design" mechanism exists**, but Anthropic's docs supply most of the parts: plan mode, a documented "adversarial review step" with a fresh-context subagent, the statement that CLAUDE.md is advisory while hooks/permissions are enforced, explicit documentation that Bash rules are not a security boundary, and (since v2.1.295, Oct 8 2026) `onFailure: "block"` for fail-closed hooks. Your R11 failure, where every cause got a bespoke hook, runs against the documented hierarchy: permission rules and sandboxing first, hooks only for logic rules can't express.
- **The most effective fix is a gated pipeline, not a better prompt**: a remedy-design skill with a fixed template (options incl. built-in / do-nothing / remove → replay matrix against incident turns and real prompts → bypass list → interaction inventory → failure mode → cost → "rejected-reasons" check), then an independent red-team subagent in fresh context, then a scripted replay test of every hook. Community artifacts (Superpowers brainstorming/writing-skills, contrarian, devils-advocate, crucible red-team, agent-review-panel, ADR skills, hook test harnesses) cover each piece, but none covers the whole of R11 out of the box.
- **Treat any remedy that can't be replayed and can't fail closed as unfinished.** Anthropic's own auto-mode work is the model to copy: an internal incident log, a labeled set of real overeager actions (n=52), measured false-negative/false-positive rates (17% FNR, 0.4% FPR), and evaluation of an action's real-world effect rather than its surface text. That is exactly the replay-against-real-data step that R11 skipped.

### 2. How the biggest players handle it

- **Anthropic (verified, primary source):** The auto-mode design is a worked example of R11 done right. It starts from an internal incident log, names a threat model (overeager, honest mistakes, prompt injection, misalignment), and evaluates alternatives with data (a tool-calls-only variant "had the lowest false-negative rate still but lost the user-intent anchor"). It weighs side effects: approval fatigue and the 0.4% FPR are made "survivable" by deny-and-continue. It openly states residual risk ("not a drop-in replacement for careful human review on high-stakes infrastructure"). It also lists, in the docs, known holes for rules (broad allow rules are dropped because "the classifier never sees the commands most capable of causing damage").\[17\]
- **Anthropic internal teams (verified but thin):** The "How Anthropic teams use Claude Code" report shows TDD-first workflows (Security Engineering), feeding stack traces during incidents, and reviewing Terraform plans.\[30\]\[31\] **I found no published Anthropic practice specifically for designing agent remedies with option/impact analysis**, beyond the auto-mode post. Treat any claim otherwise as assumed.
- **Cursor / OpenAI Codex / Gemini CLI (verified via Developers Digest's Oct 9, 2026 comparison of vendor docs):** Cursor's docs say "Hook failed, action proceeds (fail-open by default)". Cursor offers `failClosed: true` per hook and fails closed on malformed output for permission hooks. Codex's docs say "Treat tool hooks as a useful guardrail, not a complete enforcement boundary" and point to sandbox and approval policy as the boundary. Gemini CLI treats "any exit code other than 0 and 2" as a warning where the action proceeds, has a 60 s default timeout, and has no documented fail-closed switch. The convergent industry position is that hooks are a guardrail and sandbox/permissions are the boundary. That directly contradicts R11's "a custom hook per cause."
- **No evidence found** of GitHub, Google or OpenAI publishing an agent-specific "remedy design review" template. Classic SRE postmortem practice (action items checked against root cause) is the closest analogue, but it is not agent-specific.

# [R12: Environment parity in Claude Code (cloud / local / Windows / phone): mechanisms, practices and community solutions (October 2026)](R12c.md)

## TL;DR
- **The "identical in cloud and locally" claim is false by documentation.**
  - A cloud session reads the shared `.claude/settings.json` only when it has one repository. User and local settings are "not read", and device managed-settings "doesn't reach a cloud session".
  - Cloud sessions "pre-approve file edits regardless of mode", and bypass mode isn't available there.
  - With several repositories, "a session with several repositories doesn't load hooks from any repository's `.claude/settings.json`".
- **There are hard blocks, but only server-side.**
  - **Bypass:** `permissions.disableBypassPermissionsMode: "disable"` in managed settings blocks bypass locally. In the cloud you need server-managed settings, because the MDM file doesn't reach a cloud session.
  - **Pushes to main:** GitHub branch protection or rulesets. The cloud GitHub proxy "doesn't limit which branches a push can update". There are also documented bugs where a cloud push went to `main` anyway (#44949).
  - **Hooks that fail:** `onFailure: "block"` (v2.1.295+) closes hooks fail-closed.
- **For Windows and the other differences, portability is designed in, not assumed.**
  - Exec-form hooks (`command` + `args`, no shell, v2.1.139+) that call `node`/`python` scripts with no dependence on jq or Git Bash.
  - State kept in the project directory or git, not in `/tmp` or `%TEMP%`.
  - Every run checks the environment it is in: a SessionStart self-check, `/status`, `/hooks`, `claude doctor`, and a CI matrix.

### B. How the biggest players do it
- **Anthropic (official):**
  - **Configuration in the repo.** The "Claude Code: Best practices for agentic coding" post (Apr 2025) recommends committing `CLAUDE.md` and `.claude/settings.json` ("we recommend checking the former into source control to share with your team").\[46\]
  - **Verification in CI.** The "How Anthropic teams use Claude Code" PDF (2025) recommends "Set up Claude to verify its own work by running builds, tests, and lints automatically" and describes using GitHub Actions.\[47\] It doesn't mention cross-OS parity or branch protection.
  - **Devcontainer for consistency.** The devcontainer docs: "Run Claude Code inside a dev container for consistent, isolated environments across your team". An earlier version said: "Mirror your devcontainer configuration in CI/CD pipelines".\[48\]\[49\]
  - **Hardened CI workflows.** In `claude-code-action`, Anthropic forces `--permission-mode auto` in every workflow and has a `workflow-hardening.yml` check that fails the build when protection is broken.\[50\]
  - **MDM templates.** `examples/mdm` in anthropics/claude-code has templates for Jamf, Intune and Group Policy (`Set-ClaudeCodePolicy.ps1` writes `C:\Program Files\ClaudeCode\managed-settings.json`).\[51\]
  - **GitLab CI** support is in beta.\[52\]\[53\]
- **Organizations (anecdotal):**
  - **Our World in Data** (docs.owid.io) states openly that cloud sessions get the repo's `CLAUDE.md`, skills, agents and the SessionStart hook "but not your personal ~/.claude/CLAUDE.md". They build the venv with `scripts/remote_setup.sh` wired as a SessionStart hook.\[54\]
  - **Omnissa Workspace ONE** has a guide to MDM rollout on Windows, macOS and Linux (`HKLM\SOFTWARE\Policies\ClaudeCode`).\[55\]
  - **Ascending** (blog): "A laptop policy does not automatically reach an Anthropic-hosted cloud session. Treat terminal, IDE, Windows, WSL, and hosted execution as separate rollout entries."\[56\]

# [R13: Enforcing Text Rules and Lessons in Every Claude Code Context](R13c.md)

## TL;DR
- **Enforce, don't describe.** Every rule a script can check belongs in `permissions.deny` or a PreToolUse/Stop/SubagentStop hook. Use exit 2 or a JSON `deny`/`block`, and set `onFailure: "block"` (v2.1.295+) so a broken hook doesn't fail open. Only the leftover judgment rules stay as text, and they get injected rather than left in a file someone has to open.
- **Copy the Superpowers pattern for owner rules.** Superpowers survives compaction verbatim because its SessionStart hook fires on `startup|clear|compact` and prints its text again each time. Its maintainer rejected narrowing the matcher because that "breaks superpowers after every compaction or clear". Register your own owner-rules hook the same way, and add a SubagentStart hook, because SessionStart context doesn't reach subagents. Put it at user or managed scope so every project and helper gets it.
- **Some gaps have no clean fix.** No hook can change a subagent's system prompt (feature request #23885), and rewriting a spawn's model through PreToolUse `updatedInput` has been reported as ignored (#39814). Read deny rules are "best-effort" and leak through `grep -r .`, `find` and script one-liners. Hiding `MyBest/` completely needs a Read deny, the OS sandbox and an output-filter hook together, or a container that doesn't mount the folder.

# [R14: Making Claude Code obey its own runtime and harness mechanics, with enforcement mechanisms and practices (October 2026)](R14c.md)

## TL;DR
- **Most R14 sub-issues have an official hard switch.** These include `CLAUDE_BASH_MAINTAIN_PROJECT_WORKING_DIR=1` (cwd drift), the `background: true` frontmatter field and the background-by-default subagents of v2.1.198, `CLAUDE_CODE_SUBAGENT_MODEL` with `_FORCE=1` (model), the `effort` frontmatter field and `CLAUDE_CODE_EFFORT_LEVEL`, `autoCompactWindow`/`/autocompact` (context budget), the built-in sleep block, and the Monitor tool. Waiting, peeking and polling are covered only by tool-description prose ("do NOT sleep, poll, or proactively check on its progress"; "Don't peek"), and that is exactly the part the model breaks.
- **Close the workaround gap with PreToolUse hooks that classify behaviour rather than match literal strings.** Write rules for "waiting" (sleep in any language, until/while loops, `tail`/`ls`/`cat` on `tasks/*.output`), not for "the word sleep". First-word matchers are evaded by `cd x; sleep`, `python -c time.sleep`, `timeout N bash -c 'until…'`. Back the hooks with a Stop/SubagentStop hook that reads `background_tasks`, and with a status line that shows context %.
- **No official mechanism exists for four sub-issues.** These are: (a) treating harness `<system-reminder>`s as authoritative, (b) reading notifications promptly, (c) separating a queued mid-turn message from the current order (the harness itself tells the model to "address the message above as you continue this turn"), and (d) making the model actually use a loaded tool. Partial mitigations exist: `chat:queueSubmit` (Ctrl+X Enter), a Stop-hook queue file, hook-injected state, and `alwaysLoad`/`ENABLE_TOOL_SEARCH`. Treat these sub-issues as residual risk and verify them after the fact.

# [R15 Owner Communication and Standing Conventions in Claude Code: Every Known Fix, Ranked](R15c.md)

## TL;DR

- **Root cause confirmed by Anthropic.** CLAUDE.md and output styles are probabilistic: "Claude treats them as context, not enforced configuration. To block an action regardless of what Claude decides, use a PreToolUse hook instead." Of the three R15 mechanisms (rules compete with content, nothing measures output, nothing checks at the moment of action), prompt-side fixes touch only the first. Hooks are the only native layer that covers the second and third.
- **Best combined stack.** (1) Short, positively phrased rules in CLAUDE.md plus a custom output style with `keep-coding-instructions: true` and the `language` setting. (2) A UserPromptSubmit/SessionStart hook that re-injects a five-line style card. (3) A Stop hook that lints `last_assistant_message` and blocks once with a concrete rewrite reason. (4) PreToolUse guards on commit/PR for ZMIANY, the version bump and the backup report. (5) A PostToolUse/PostToolBatch "silence counter" that asks for a one-sentence update after N silent tool calls. (6) A forced skill-evaluation hook that requires a stated reason when a skill is skipped. (7) `/doctor prompt-audit` plus a spell/stale-reference check for CLAUDE.md.
- **What you cannot fully fix.** A chat reply cannot be blocked before the owner sees it. A Stop-hook rewrite appears below the faulty reply. Read-deny rules hide file contents but probably not folder names in `ls`/Glob output. Read-vs-Bash has no official resolution beyond the fact that a single-file `cat`/`head` counts as a read. Mark those residual risks rather than expecting zero violations.

# [R16 — Making Claude Code Surface Knowledge-Base Gaps and Overgeneralisations: Mechanisms, Practices and Ready-Made Solutions (state as of 11 Oct 2026)](R16c.md)

## TL;DR

- **Officially available building blocks:** Anthropic has documented primitives for each sub-aspect, but not a finished solution. The primitives are Stop/SubagentStop `decision: "block"`, prompt and agent hooks, PostToolUse feedback, SessionStart `additionalContext`, `InstructionsLoaded`, the `AskUserQuestion` tool (which hooks can match), subagents with restricted tools, and the guidance to "allow Claude to say I don't know", ground in direct quotes and retract claims that have no quote. There is **no official mechanism** for provenance tagging, local doc mirroring, staleness detection of a knowledge base, or "offer the owner a choice" enforcement. Those have to be built from hooks.
- **What the big players do:** Anthropic keeps writing and verification apart. Its Research system runs a separate CitationAgent over the sources and the report, and its evals score "factual accuracy" and "citation accuracy" separately. It keeps state in external files (claude-progress.txt, a JSON feature list it chose because models are less likely to overwrite JSON) and tells users to give Claude a pass/fail check and to have Claude "interview" them with `AskUserQuestion`. GitHub's Spec Kit makes uncertainty explicit with `[NEEDS CLARIFICATION]` markers and blocks on a checklist item "No [NEEDS CLARIFICATION] markers remain".\[1\]
- **Recommended stack for this project:** (1) frontmatter provenance and a `claim_type` tag on every `knowledge/` entry; (2) a PostToolUse lint hook on writes to `knowledge/**` and output docs that rejects untagged claims, citations with no local mirror, and quotes that do not appear verbatim in the mirror; (3) a scope-checker agent hook or subagent for overgeneralisation; (4) a `gaps.md` ledger plus a Stop hook that blocks until every gap has been presented through `AskUserQuestion`, with a PostToolUse hook on `AskUserQuestion` recording the owner's choice; (5) a SessionStart hook that compares `claude --version` and the in-session tool list with the version stamps on every "Claude Code self-knowledge" claim.

### 2. How the biggest players handle it

**Anthropic Research (multi-agent research system, 2025).** An orchestrator-worker design. After research, "a specialized CitationAgent … processes documents and the research report to identify specific locations for citations, ensuring all claims are properly attributed to sources."\[19\] The point of the separate agent is that it checks claims against the raw documents, not against the lead agent's memory of them.\[20\] Evaluation uses an LLM judge with separate rubric items: "Factual accuracy — do claims match sources? Citation accuracy — do cited sources match claims?" and "Source quality — did it use primary sources over lower-quality secondary sources?"\[21\] *Mapping:* this is the model for (a) and (c). Separate the writer from a verifier that has only the sources and the output.

**Anthropic context engineering (29 Sep 2025).** "Structured note-taking, or agentic memory, is a technique where the agent regularly writes notes persisted to memory outside of the context window… Like Claude Code creating a to-do list, or your custom agent maintaining a NOTES.md file."\[22\] *Mapping:* (b). Observed runtime behaviour (thresholds, env vars) must be written to a file the moment it is observed, not left in context.

**Anthropic long-running harness (26 Nov 2025, Justin Young).** An initializer agent creates "a claude-progress.txt file that keeps a log of what agents have done" and a feature list in which features start as "failing". "We prompt coding agents to edit this file only by changing the status of a passes field… we landed on using JSON for this, as the model is less likely to inappropriately change or overwrite JSON files compared to Markdown files."\[23\] *Mapping:* (b) and (e). Keep the gap ledger as JSON with a status field that the agent may only advance (`open → presented → decided`), never delete.

**How Anthropic teams use Claude Code.** Teams maintain CLAUDE.md files in git and use "end-of-session documentation updates", a loop in which Claude Code helps refine the Claude.md files based on actual usage.\[24\]\[25\] Boris Cherny's widely reported workflow (InfoQ, Jan 2026) says "the most important tip is to give Claude a way to verify its work through a feedback loop."\[26\] *Mapping:* (b). End every session with an explicit "what did I observe that is not in `knowledge/`?" step, enforced by a Stop hook.

**GitHub Spec Kit.** Its spec-driven methodology tells the agent to "Mark all ambiguities: Use [NEEDS CLARIFICATION: specific question]" and "Don't guess", and its quality checklist contains "No [NEEDS CLARIFICATION] markers remain".\[27\] `/speckit.specify` caps markers at 3 and presents options to the user,\[28\] and `/speckit.clarify` replaces each marker with the user's answer.\[29\]\[30\] Issue #2181 proposes rendering these through Claude Code's native `AskUserQuestion`.\[31\] The Xebia guide warns that the markers "only catch what the model identifies as ambiguous".\[30\] *Mapping:* (a) and (e). It is the most mature public convention for turning uncertainty into an explicit, machine-checkable marker.

**Karpathy's "LLM Wiki" pattern (2026) and successors.** The gist defines a Lint operation: "contradictions between pages, stale claims that newer sources have superseded, orphan pages… data gaps that could be filled with a web search."\[32\] rohitg00's "LLM Wiki v2" makes the R16 point exactly: "Confidence 0.85 doesn't distinguish 'verified from official docs' from 'the agent guessed this last session.' Without an Epistemic Layer, inferences written back into memory become indistinguishable from sourced facts." It proposes tracking "Claim Provenance (source chain)".\[33\] *Mapping:* (a), (b) and (d).

**Academic practice.** The "Claude Code Complete User Handbook" (arXiv 2608.26742) keeps a verification ledger. Each product claim "was adjudicated against the raw text of the primary documentation page", summaries were discarded when they disagreed with raw text, and claims that could only be settled against a running CLI appear "as UNVERIFIED in the open list… with the local check that closes it". It was verified against CLI 2.1.241 and re-verified against 2.1.246.\[34\] *Mapping:* this is a ready template for (a) and (d): version-stamped claims plus an explicit UNVERIFIED list with closing checks.
